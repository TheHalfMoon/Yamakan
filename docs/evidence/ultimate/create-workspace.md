# The Create workspace

Part of issue #203.

**Without Kaggle set up it does not start a model:** the page says so and nothing in it offers to generate. **With `YAMAKAN_KAGGLE_CLI` and `YAMAKAN_KAGGLE_USERNAME` set, a person can start a real run from the page,** on their own private notebook, by the founder's decision "Yamakan drives Kaggle" (`docs/FOUNDER_DECISION_RECORD.md`). `ENGINE_ENABLED` and local recipes are unchanged: this route does not turn on any engine on this machine.

## Starting a real run

- Text to video only: the prompt and seed leave this computer, no media does. A person ticks that they agree, every run, and presses the button.
- The Kaggle CLI uses its own token. Yamakan never reads it, and passes the CLI fixed arguments; the prompt travels inside a file, as base64 of JSON, so it cannot become Python or a command.
- The notebook is asked to be private, with a 60-minute limit. Kaggle's own answer on privacy is read before a push to an existing notebook, and nothing is sent if it does not say private or cannot be read. A new notebook has no answer to read, and it is asked to be private. Kaggle's words for a missing notebook are the same as for a refusal, so a notebook counts as new only when a search of the account's own notebooks, which needs working credentials, does not find it and has no further page. That list and its answer for a missing name were read on real Kaggle. After a push it is read again, and because the run is then already going, a bad answer warns beside the run rather than ending it. A notebook still running is not replaced. Kaggle keeps each prompt in the notebook's history, and the page says so.
- Kaggle's latest output could be another run's, so a result counts only if its receipt names this run, passed its own checks, and matches the video's hash.
- **Yamakan cannot stop a run on Kaggle.** The CLI has no such command, and the SDK's call needs a session ID the public interface does not give, tried on 2026-11-06. So the page offers Stop following, says the run goes on using quota, and links to its notebook.
- **A run survives a restart.** It is recorded in the job table before anything is sent, under the name its receipt will carry, and the page finds it again in the project. It is followed, and never sent again: it enters that table in a state the job pump cannot claim, a restart leaves it alone, and the job commands refuse to retry it. After a push is tried, only a definite refusal counts as not sent: anything else is said to be uncertain, and stays so until the run's own result proves it arrived, since a notebook's state could be another run's. A run past its time limit is not ended by the clock: it says so, and is still asked, since a finished video may be waiting and a blip must not lose it. Only a result, or Kaggle's own answer, ends it, and a person can stop following it at any time, which does not stop it on Kaggle. A new run is not sent while another run of that model is still being followed in any project of the workspace: it is asked about first, which collects it if it has finished, and if it cannot be, the start is refused and names the project. Stopping following clears that, and does not stop it on Kaggle. An error page the CLI saves as the file it asked for, or a receipt it did not bring, is fetched again, not taken for the run's end: four times over a quarter of an hour, after which the run ends as failed, saying any result is still on its notebook. A refusal from Kaggle about a notebook is checked against the account's own list before it is read as a new notebook, and a run sent from another account is not asked about. A restored copy of the workspace does not follow, import or resend the original's run. The prompt is therefore kept in the workspace's database and its backups, stays there after a run is dismissed, and can be read by anything with read access to the project, as its stories already can.
- A status is what Kaggle says. There is no percentage, because it gives none; only the time so far.

- After a run, only its video stays on this computer, in a temporary folder; its script is removed once pushed. Folders over a day old are removed the next time a service first uses Kaggle, not on a timer, unless they hold a video still waiting to be brought in. The temporary folder is shared, so a second workspace's sweep or a temp cleaner could remove such a video. It is then fetched from Kaggle again only while that run is still the notebook's latest, and a person's new start can replace it there, with no warning. A start in a restored copy of a workspace can likewise replace the original's uncollected result, once the nine minutes have passed. So can a start from another workspace on the same Kaggle account, which has no record of this one's runs.
- Only a model with its own tested run from the page is offered: Wan2.2-TI2V-5B. CogVideoX-2b says it has not been tested from this page.

**Places and props.** A place, prop, wardrobe or style can be kept from a PNG or JPEG, and pinned to a shot that has a video. Each is an ordinary reference pack in the project, and a shot pins one version by hash, so a newer version changes no shot until it is pinned again. `npm run qualify:create` does this once in Edge at desktop width in English, through a reload. Its phone and Arabic checks then only measure that the page has no sideways scroll, and take a picture. **These are records only.** No model receives them, a generation's request carries none of them, and they do not make shots consistent with each other. The consent check on a first frame reads every pack in the workspace, and forwards nothing from them. An agent a person has connected can read them, as it can any document in the project. Saving one, or a pin, ends undo for what came before, and the page says so. Importing its image already did. A pin is on a shot that already has its video, so it does not record what that video was made from. Nothing here can tell what a picture shows: choosing "prop" for a photo of a person is not stopped, and the page only asks that it not be done. Media whose consent was revoked can be kept and shown here, though placing or generating from it stays refused. Choosing an image before a shot has a video keeps the element, with no shot to pin it to yet.

**Pictures to compare against.** `npm run qualify:create` compares the Places and props panel with a picture kept in `docs/evidence/baselines/`, in English and in Arabic layout, and fails if more than 0.2% of its pixels differ by more than 16 of 255. There is a set for each system, and only Windows has one. On any other system it says it has no picture and goes on. This check is not in CI. It shows the panel has not moved since the picture was accepted. It does not show that it reads or looks right, which stays a person's judgement. Run with `YAMAKAN_UPDATE_BASELINES=1` to replace a picture, after looking at it.

`npm run qualify:kaggle` ran this for real, through export. Its receipt, `kaggle-page-run-receipt.json`, names the commit it ran at. Failure-path changes after that commit were tested with the stand-in only. The engine's failure, wrong-run, privacy and unknown-run paths are tested with a stand-in for Kaggle in `tests/kaggle-engine.test.ts`. **The panel's real runs cover success and a restart:** at commit `48623d7` a real run with the service killed partway found the same run after the restart, brought its video in and placed it on the timeline, as `kaggle-restart-run-receipt.json` records. It stopped at the export step on a bug in the test script, since fixed. Later commits on the same work were tested with the stand-in only, because Kaggle then answered that the account's weekly GPU quota of 30 hours was used up. That refusal, at `a799737`, was real, and the page showed it as a refusal, as `kaggle-quota-refusal-receipt.json` records. That nothing is left to follow after a refusal is tested with the stand-in. Its failure and Stop following screens, and finding a run after a start's answer is lost, have not been run in a browser. How long a stale status lasts on Kaggle is assumed to be under three minutes, not measured. After a send Kaggle did not refuse, another is refused for nine minutes: the longest a send can take, six minutes, plus that three. The six assumes a timed-out CLI really stops on Windows: if one never returned, that model could not start again until Yamakan was restarted, and nothing would say so. After Stop following, a new run is then refused until Kaggle says the old one ended: up to its 60-minute limit, about 19 minutes for a normal run. A first run on a new notebook was not exercised on real Kaggle; what Kaggle says of a missing notebook was.

## What works now

`npm run qualify:create`, real Edge against the real service, by the interface unless noted:

- Write a shot and choose a model and seed. Shot, movement, lens and light add words to the prompt, and the exact text a model would be given is shown. The page says these are only words: neither model has camera settings, and it may not follow them.
- A shot being written stays across a reload, per project, in this browser's storage: it does not move with a backup and is lost if site data is cleared. **A made video's record is kept in the project,** as a shot and take in a story titled "Made in Create", so it survives a cleared browser and goes with a backup. It holds what the receipt said, as the receipt's claims. The page calls it the project's record, because a story can be written by hand: it is not proof. Saving it is a new revision, as any story save is, and ends undo past that point. `npm run qualify:create-durable` checks this with real Edge and the real service, on a test pattern: a save made to fail says so and claims no success, trying again makes one shot and no second asset, and the record stays the same bytes in a fresh browser profile, after the service restarts, and on Yamakan started from a restored backup. A real generation's record has been checked across cleared browser storage only, by `qualify:kaggle`. Trying again for a generated video goes by bringing it in again, which returns the same asset; that was not forced to fail in a browser.
- Bring a video in, with its run receipt. A video that is not the receipt's file, a receipt from a run that did not finish or did not pass its own checks, and a video over 512 MiB with a receipt, are refused and nothing is imported. **A match shows only that the file is the one the receipt describes.** Anyone can write a receipt, so its model, seed and prompt are its claims.
- Add it to the timeline, open it in Edit, and export with the toolbar's button: a decodable H.264 file.
- A file converted to a constant frame rate on the way in says its original matched the receipt, not this copy. A placed video keeps its whole length, where a clip placed from the media list stops at 5 seconds.
- Keyboard: the panel's main controls are reached by Tab, model before bring-in. Every field has a name. No sideways scroll at 390 px. Arabic lays out right to left. **The Arabic wording has had no native review.**

The check's default video is a test pattern with a receipt written by the check, so it qualifies the path and is not AI output. The check takes a real video and receipt as arguments. Its screenshots were looked at by the builder; **no pixel comparison against a saved baseline exists yet.**

## Not done

Image-to-video; stopping a run on Kaggle; CogVideoX started from the page, whose script took the same change but was not run this way; reference images a model receives, and characters or anything else with a person's likeness in it; refusing a placement on a locked track is written but not exercised by the check; a person's check of how this reads and feels.

Model facts on the page are what has been run: sizes, frames, rates and times, not everything each model can do. CogVideoX's are from `first-ai-video.md`; Wan's 19 minutes is a real run from the page; the runs took 19 to 20.

## What was studied

Higgsfield, signed out, 2026-11-06. Nothing was signed into, generated or paid for, and no optional cookies were accepted. Its code, copy, assets and brand are not in Yamakan; screenshots stay outside this repository.

**Seen, on public pages, with Craft Anything 0.3.0 in clean-room mode and then the app's built-in browser, because the tool's scripted walkthrough is not offered in clean-room mode:**

- Generation pages are one composer: a prompt with a row of controls showing their current value, including model, resolution, ratio, length and count.
- Above Cinema Studio's prompt, chips for references with a counter, film setup, camera, colour palette and lighting, each showing "Auto" by default.
- Generate shows its price on the button, before anyone signs in.
- Film setup opens a panel with Genre, Era and Tempo sections.
- The Camera chip opens a sign-in screen, so that is where this stopped.

**Not seen:** the Camera panel; Era and Tempo's contents; the model list; a generation's progress, failure or result; the editor; export. Anything said about those would be assumption. Keyboard behaviour was not tested there.

**What Yamakan took from this:** the idea that a person should see every setting's current value beside the prompt, and the cost before they commit. Yamakan's cost is time on a free GPU. It did not take the look, and no control here claims more than adding words to a prompt.
