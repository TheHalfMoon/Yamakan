# Security and privacy gates — final proposal

Scope is a local trusted account, one granted workspace, loopback service and explicitly bound stdio clients. It is not internet tenancy or a defense against the same account rewriting data/hashes. Controls below are proposed unless linked to an executed receipt; types and static graphs are not enforcement. [Contracts](OPERATIONAL_CONTRACTS.md), [source exclusions](SOURCE_IMPORT_MATRIX.md) and [acceptance](E2E_ACCEPTANCE.md) define executable gates.

Mandatory exclusions retain ArtCraft browser_emulation/consumer-cookie clients and broad Tauri configs, filmmaker unvalidated Electron/file/shell IPC, OGA provider/download authority, OpenCut browser persistence/global managers/canonical export and Kodac fallback-secret authentication. Founder source authorization does not grant unrelated assets, weights, trademarks or hosted capacity. Process isolation does not itself remove license/distribution obligations.

Physical power loss/hardware flush, external media directory durability, native exploit sandboxing and same-account adversary protection are not proven. Bounded probes/timeouts cannot prevent every codec exploit. An internal local preview can keep decoder sandbox deferred only with that residual risk explicitly accepted under J and a known-vulnerability/binary review; stronger public security claims or untrusted multi-user media require qualified OS containment. The accepted MVP gates still include adversarial inputs and zero egress, not an assertion of sandbox perfection.

Crash recovery preserves original DB/WAL/SHM/corrupt media; a page-level DB failure is diagnostic mode, not a safely skipped row. Renderer/workers receive staging inputs/output keys and no writable DB handles, tokens or project grants; validate/fence outputs before publication. Full-process sandbox/egress grants for optional engines need actual runtime enforcement, not Ecra/kernux policy types. Remote collaboration and cloud resale remain disabled.

Release requires exact-head independent review, real Windows fault/ACL/backup/network/parity tests, dependency/binary SBOM/notices/source offer and clean install/update/rollback. An OCR delegate result, Jev verdict, static REA graph or Linux prototype pass cannot approve the release. [Founder packet](FOUNDER_DECISION_PACKET.md) names the remaining decisions.

**W4 / Q15 residual (transport-bound principals):** Human-only commands (`agent:create`, `agent:revoke`, `director:approve`, consent grant/revoke) require the in-memory browser principal obtained through a single-use launch secret (60 s TTL). Q15 OS user-presence confirmation is not wired yet; a same-account process that can drive the browser, read its memory, or consume a fresh launch secret before the user does remains in scope for that window (the second exchange fails with “link already used”).

**That window is any time, not only the 60 s after the user opens a link.** Found in the security check of 2026-11-08. A process running as the user can make a fresh link whenever it likes: it can run `npm run open`, or write `<workspace>/launch` itself, since the folder is the user's. It then posts the secret to `/api/v1/session` with a hand-set `Origin: http://127.0.0.1:<port>`, which any program can send, and receives the browser session. That reaches every human-only command: grant or revoke consent, approve Director stages, create agents. No click by the user is involved. So **the human-only rule holds only against a process that cannot read or write the workspace folder.** An agent given the workspace token, or run as the user with file access, as the README describes for the CLI and for MCP run with `YAMAKAN_MCP_LOCAL_CLIENT=1`, is in that class.

Until Q15 OS user presence is wired into each human-only command, these hold:

- An agent meant to be bound by its grant runs under a separate Windows account, or in an AppContainer, with no access to the workspace folder, and is given only its own agent token (`YAMAKAN_AGENT_TOKEN_FILE`), never the workspace `token`. The person makes, lists and revokes these tokens in Finish → Agent tools → Agent access.
- A client with a token (the CLI, MCP, the SDK) sends it only to a service that has first proved it knows it: `GET /api/v1/hello` with a fresh challenge and a one-way id of the token, answered by an HMAC of the challenge keyed by the token's hash (`sdk/service-proof.ts`). A process that took the port first cannot answer, so it never receives the token. The browser page's launch link is not covered by this: a process that took the port before the page opened would still receive that one-time secret.
- The MCP server refuses to start without an agent token (`YAMAKAN_AGENT_TOKEN_FILE` or `YAMAKAN_AGENT_TOKEN`). Running it as the full local client, with the workspace `token`, takes `YAMAKAN_MCP_LOCAL_CLIENT=1`: a choice made by name, never a fallback.
- An agent run as the user, with the workspace token or file access, is trusted as the user: what it does counts as the user's own act, including consent and approvals.
- Moving the launch secret into the service's memory would not help, because the launcher proves itself with the same file access. Zero-cost assessment (UserConsentVerifier preferred; procd stays dependency-free; no Q15 pass claimed): [`evidence/qualification/q15-user-presence-assessment.md`](evidence/qualification/q15-user-presence-assessment.md).

## Blender worker (2026-11-10)

- Blender renders run only through yamakan-procd on Windows, in the engine-worker profile: an AppContainer with no network capability and no GPU, a low-integrity token, a kill-on-close Job Object (at most 4 processes, 30 minutes, 4 GiB committed memory). It may read only its own install, Yamakan's one fixed script (`scripts/blender/yamakan_render.py`) and that render's scene description, and write only that render's frames folder.
- It runs `-b --factory-startup -Y --offline-mode -noaudio`: factory settings, Python embedded in .blend files never auto-runs, no online access. Yamakan hands it a bounded JSON scene (`core/blender/scene.ts`), never Python; the script re-checks every value.
- The runtime is the pinned official build, checked by SHA-256 before each use, installed from a zip the person downloaded (`npm run blender:install`, which also verifies the zip's hash). It runs in place inside procd's worker tools folder, whose read-and-execute grant its files inherit (procd's run-in-place rule, `native/procd/src/container.rs`).
- Its frames are checked against the scene (count, size, receipt) before Yamakan's own FFmpeg, reading only those frames and only PNG, encodes them; the video is probed before it joins the project.
- Not covered yet: macOS and Linux (no contained worker there, so no Blender); GPU rendering (EEVEE, Workbench) needs a GPU the container does not give.
