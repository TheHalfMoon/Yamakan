# Security and privacy gates — final proposal

Scope is a local trusted account, one granted workspace, loopback service and explicitly bound stdio clients. It is not internet tenancy or a defense against the same account rewriting data/hashes. Controls below are proposed unless linked to an executed receipt; types and static graphs are not enforcement. [Contracts](OPERATIONAL_CONTRACTS.md), [source exclusions](SOURCE_IMPORT_MATRIX.md) and [acceptance](E2E_ACCEPTANCE.md) define executable gates.

Mandatory exclusions retain ArtCraft browser_emulation/consumer-cookie clients and broad Tauri configs, filmmaker unvalidated Electron/file/shell IPC, OGA provider/download authority, OpenCut browser persistence/global managers/canonical export and Kodac fallback-secret authentication. Founder source authorization does not grant unrelated assets, weights, trademarks or hosted capacity. Process isolation does not itself remove license/distribution obligations.

Physical power loss/hardware flush, external media directory durability, native exploit sandboxing and same-account adversary protection are not proven. Bounded probes/timeouts cannot prevent every codec exploit. An internal local preview can keep decoder sandbox deferred only with that residual risk explicitly accepted under J and a known-vulnerability/binary review; stronger public security claims or untrusted multi-user media require qualified OS containment. The accepted MVP gates still include adversarial inputs and zero egress, not an assertion of sandbox perfection.

Crash recovery preserves original DB/WAL/SHM/corrupt media; a page-level DB failure is diagnostic mode, not a safely skipped row. Renderer/workers receive staging inputs/output keys and no writable DB handles, tokens or project grants; validate/fence outputs before publication. Full-process sandbox/egress grants for optional engines need actual runtime enforcement, not Ecra/kernux policy types. Remote collaboration and cloud resale remain disabled.

Release requires exact-head independent review, real Windows fault/ACL/backup/network/parity tests, dependency/binary SBOM/notices/source offer and clean install/update/rollback. An OCR delegate result, Jev verdict, static REA graph or Linux prototype pass cannot approve the release. [Founder packet](FOUNDER_DECISION_PACKET.md) names the remaining decisions.

**W4 / Q15 residual (transport-bound principals):** Human-only commands (`agent:create`, `agent:revoke`, `director:approve`, consent grant/revoke) require the in-memory browser principal obtained through a single-use launch secret (60 s TTL). Q15 OS user-presence confirmation is not wired yet; a same-account process that can drive the browser, read its memory, or consume a fresh launch secret before the user does remains in scope for that window (the second exchange fails with “link already used”).

**That window is any time, not only the 60 s after the user opens a link.** Found in the security check of 2026-11-08. A process running as the user can make a fresh link whenever it likes: it can run `npm run open`, or write `<workspace>/launch` itself, since the folder is the user's. It then posts the secret to `/api/v1/session` with a hand-set `Origin: http://127.0.0.1:<port>`, which any program can send, and receives the browser session. That reaches every human-only command: grant or revoke consent, approve Director stages, create agents. No click by the user is involved. So **the human-only rule holds only against a process that cannot read or write the workspace folder.** An agent given the workspace token, or run as the user with file access, as the README describes for the CLI and for MCP run with `YAMAKAN_MCP_LOCAL_CLIENT=1`, is in that class.

Until Q15 OS user presence is wired into each human-only command, these hold:

- An agent meant to be bound by its grant runs under a separate Windows account, or in an AppContainer, with no access to the workspace folder, and is given only its own agent token (`YAMAKAN_AGENT_TOKEN_FILE`), never the workspace `token`. The person makes, lists and revokes these tokens in Finish → Agent tools → Agent access.
- A client with a token (the CLI, MCP, the SDK) sends it only to a service that has first proved it knows it: `GET /api/v1/hello` with a fresh challenge and a one-way id of the token, answered by an HMAC of the challenge keyed by the token's hash (`sdk/service-proof.ts`). A process that took the port first cannot answer, so it never receives the token. The browser page's launch link is not covered by this: a process that took the port before the page opened would still receive that one-time secret.
- The MCP server refuses to start without an agent token (`YAMAKAN_AGENT_TOKEN_FILE` or `YAMAKAN_AGENT_TOKEN`). Running it as the full local client, with the workspace `token`, takes `YAMAKAN_MCP_LOCAL_CLIENT=1`: a choice made by name, never a fallback. The tool list an agent is shown leaves out what its token may not call (`docs/AGENT_MCP_ARCHITECTURE.md`): that list is presentation, and the gate is `authorize`, at every call.
- An agent run as the user, with the workspace token or file access, is trusted as the user: what it does counts as the user's own act, including consent and approvals.
- Moving the launch secret into the service's memory would not help, because the launcher proves itself with the same file access. Zero-cost assessment (UserConsentVerifier preferred; procd stays dependency-free; no Q15 pass claimed): [`evidence/qualification/q15-user-presence-assessment.md`](evidence/qualification/q15-user-presence-assessment.md).

## Blender worker (2026-11-10)

- Blender renders run only through yamakan-procd on Windows, in the engine-worker profile: an AppContainer with no network capability and no GPU, a low-integrity token, a kill-on-close Job Object (at most 4 processes, 30 minutes, 4 GiB committed memory). Besides what every AppContainer may read (system files), it may read procd's worker tools folder (its own install and the other staged tools there, all shared by the one worker container), Yamakan's one fixed script (`scripts/blender/yamakan_render.py`) and that render's scene description, and it may write only that render's frames folder.
- It runs `-b --factory-startup -Y --offline-mode -noaudio`: factory settings, Python embedded in .blend files never auto-runs, no online access. Yamakan hands it a bounded JSON scene (`core/blender/scene.ts`), never Python; the script re-checks every value.
- The runtime is the pinned official build, installed from a zip the person downloaded (`npm run blender:install` checks the zip's SHA-256 and every byte of the extracted tree before it is used). Before every render, the install's listing (every file's name and size, no links) and the bytes of everything Windows runs from it (`*.exe`, `*.dll`, `*.pyd`) are checked against pins; every byte of the whole tree is checked on the first render after the service starts and then once a day. Not caught: a same-user process changing a script or data file without changing its size between two full checks; what it runs then still runs inside the contained worker. It runs in place inside procd's worker tools folder, whose read-and-execute grant its files inherit (procd's run-in-place rule, `native/procd/src/container.rs`), which skips procd's own byte check for any tool under that folder, so the service verifies such a tool itself before running it.
- Its frames are checked against the scene (exactly the frames asked for, each a plain file of its own no larger than an uncompressed frame, and a receipt that names Blender 5.3.0 and offline mode) before Yamakan's own FFmpeg, reading only those frames and only PNG, encodes them; the video is probed before it joins the project.
- Not covered yet: macOS and Linux (no contained worker there, so no Blender); GPU rendering (EEVEE, Workbench) needs a GPU the container does not give.
- Known limit: one Blender render runs at a time across all projects and principals; a second is refused, not queued, so a principal with `render:execute` (an agent token) can keep the one slot busy until someone with `job:control` cancels its render.

## Approvals of what leaves this computer (MPR-204)

**Denied by default.** Without a person's approval no Kaggle CLI is started and no run is recorded or sent. Where each kind is asked for:

- **Contacting** (`egress`): in `kaggleCli` (`core/engines/kaggle.ts`), the one place that starts the Kaggle CLI, before every start of it, following a run included; and once more before a send writes anything. Its `mayConnect` cannot be left out. A CLI that is already running (a push for at most 3 minutes, an output for at most 5) is not stopped when an approval closes. (Ending a CLI that ran too long starts the system's own `taskkill`, which is not asked for.)
- **Using an allowance** (`spend`): in `createGenerationService().start` (`core/engines/generation.ts`), after every other check of `start` and before a run is recorded or sent. Its `permit` cannot be left out and answers at once; for Kaggle it counts one run of both kinds in one transaction, at most the whole script's bytes and the recipe's time limit, and never gives one back, also when the engine then refuses the run (the notebook is busy or not private, a run was sent minutes ago, a picture is too large) or Kaggle does. Just before the push, which can be minutes later, both approvals that the run was counted on are asked about again: revoked, over, void or under other settings, nothing is pushed. A ComfyUI on this computer has `noRemoteUse`.
- **Downloading:** nothing here downloads. `requireGate` with `download` always refuses, and code that would must ask it first.

An approval that closes while a run is being sent refuses the run; it is never taken for one that may have left. One that closes while a run is followed stops every contact: the run is shown as unknown with the reason, is never marked failed for it, goes on using the allowance on Kaggle, and is followed again once a person approves again. Stopping to follow a run needs no approval. `tests/gates.test.ts` holds the list of the files in `core`, `server`, `cli` and `mcp` with an outbound call, and how many each has, by their text: a call made in another way, by a dependency, or by `sdk/` is not seen by it, and programs that are started have a list of their own (`processSpawnAllowlist`).

- **What an approval is.** A row a person at the browser records with `yamakan.gates.approve`: its kind (contacting a route's host, or using its allowance), the route and its one host (`kaggle.com`), the configured account, the purpose, when it ends, how many runs and how many bytes or seconds, who gave it, the workspace's epoch, and whether a proxy and whether a certificate setting was there (OA-20), never their values. It is never changed. Revoking it and using it are rows of their own, and a use is never given back.
- **What it allows.** Exactly that kind, route, host, account and purpose, by equal text; the newest approval of a place is the one that counts. It allows nothing once it has ended (or while this computer's clock is before it), is revoked, is used up, or was given under other network settings. One for contacting that is used up still allows following what was counted on it. A restore brings none back: the tables are removed whatever a backup holds in them, whatever version it claims, and made again empty; and a backup whose epoch cannot be raised, or that sets back the epoch or a revoked agent token while it is restored, is refused. A restore works without the backup's foreign keys, which could have done that. A download cannot be approved, and a row for one that someone planted allows nothing.
- **Who.** `yamakan.gates.approve`, `.list` and `.revoke` are for the browser session only, under the consent scopes that no agent can hold. They have the residual of W4 / Q15 above: a process of the same account that can drive the browser can approve.
- **What it does not cover.** The host is what Yamakan approves and passes on; which hosts the Kaggle CLI then contacts is the CLI's own (MPR-205). The network facts are read from the names that the service's environment would give the CLI. Not seen: a proxy set in Windows itself or in the CLI's own settings file, one proxy or certificate replaced by another, a `NO_PROXY` that comes or goes, and a `KAGGLE_` name that looks like neither (those that hold PROXY, ENDPOINT, HOST, URL, SSL, CERT or VERIFY, or the word CA, count). What a local ComfyUI and its nodes do is their own. A same-account process that can write the workspace database can write a row.
