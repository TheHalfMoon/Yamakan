# Yamakan offline MVP — release proposal (T10)

**Frontier:** main `951f4be5` (2026-10-13), with PR #21 (frozen performance policy) and PR #22 (journey fixtures and interruption tests) merged. Rows changed since T10 cite their PR.

**Verdict: NO-GO for release.** T1–T9 are merged with independent review and exact-head CI, and every gate measured on this machine passes its frozen threshold (performance: founder approval I; resources: agent decision under the continuation directive). But the [MVP acceptance](E2E_ACCEPTANCE.md) requires every row to pass on the exact release commit **and artifact hashes, on clean Windows Profile A**. Several rows need a pinned distributable bundle, a clean profile, a second account, a native Arabic reviewer, harnesses that do not exist yet, or worker read containment (release-blocking). This document is the gate-by-gate account behind the ship decision.

**Measured at commit `df3b11c1`:** receipt [`docs/evidence/qualification/t10-release.json`](evidence/qualification/t10-release.json), produced by `npm run qualify:release` on a clean tree. The run rebuilds the native helpers and the interface before hashing. The release run must be repeated at the exact release head.

**Found and fixed while qualifying:** FFmpeg's `-threads` applies to one input, so exports decoded every clip after the first with one thread per core, and conversions encoded without a thread limit. Every input and encoder now gets the policy's two threads; the heavy export's peak fell from 1,522 to 985 MiB and the conversion's from 677 to 274 MiB.

A worker at its limit fails on allocation and exits non-zero (tested). The corpus is synthetic test patterns: it bounds the listed codecs at the listed sizes with up to six simultaneous sources, not every possible input; a longer timeline with more simultaneous heavy sources uses more memory and fails at the limit rather than exceeding it.

### Offline evidence (two checks, network enabled)

- **Browser pages.** The E2E records every request any page of the journey makes and asserts that each one is to 127.0.0.1, in-page data (`blob:`, `data:`), or the browser's own built-in pages (`edge:`, for example its download panel). Result: 142 requests, 0 external. This covers fonts, previews and media loaded by the interface. The page's Content-Security-Policy (`default-src 'self'`, `connect-src 'self'`) restricts the same thing.
- **Service process tree.** TCP connections and listeners of the service, procd and every FFmpeg/ffprobe worker, sampled during the E2E. Result: 9 samples about 1.1 s apart; 13 connection records; in the samples taken, 0 to another machine and 0 listeners reachable from another machine.
  - **What it cannot see:** UDP (DNS), and connections shorter than the sample gap. Short-lived workers may not have been sampled at all. Their real egress control is FFmpeg's `-protocol_whitelist file` on every probe and render.
- **Not done here:** the gate's "network disabled" run with a packet-level egress capture (for example `pktmon` or firewall auditing), which needs an administrator.

## Worker sandbox (release blocker from T4a) and its residuals

**Resolved in T9c:**

- Workers run with a restricted, low-integrity token. WMI process creation is denied to them, tested against a control that succeeds.
- Published files carry only the main data stream, in files the service creates.

**Read containment (AppContainer, this change):**

- **Design.** procd starts every worker inside one AppContainer (`Yamakan.MediaWorker`) with no capabilities except one of its own: a capability SID derived from a name unique to that worker. The restricted low-integrity token and the Job Object are kept. An AppContainer process is denied every object whose access list does not name its container, a capability it holds, or ALL APPLICATION PACKAGES, and with no network capability it cannot open a connection. A worker can therefore read only:
  - its executable, run from a byte-verified copy in a Yamakan tools folder that grants the container read and execute (`%LOCALAPPDATA%\Yamakan\worker-tools`);
  - system files that Windows grants to all application packages;
  - the files and folders its request names, granted to its own capability for its lifetime and revoked when it exits.
- **Every product worker declares what it reads:** a probe reads its file; a render reads its inputs, `titles.ass` and the fonts folder; a conversion reads its source; the title-fit and capability checks read their script. Grants are written to the one object (`SetKernelObjectSecurity`), never re-propagated through a tree.
- **Evidence** (`tests/containment.test.ts`): a stand-in hostile worker (Node running a script, as a compromised FFmpeg would run code), started through the real service's workspace, is **denied** a sentinel file outside the workspace, the service token, the launch link, `workspace.sqlite` and a second imported media object it was not given; listing the workspace and the user profile; writing to the workspace and beside the sentinel; a child process; and TCP connections to loopback and to this machine's network address. An uncontained control process does all of these. The worker **can** read its granted input and write its own folder. Afterwards no capability entry remains on the input, the folder or the current directory.
- **Lockout closed:** a worker may modify its folder's contents but not its access list; the T9c test of a worker opening its folder to everyone is now refused ("unauthorized"), and the folder is still reset when it exits.

**Residuals:**

- **Hostile-media corpus** (`tests/hostile-media.test.ts`, hashes in the test diagnostics): 11 malformed or adversarial files (truncated and garbage MP4, a ZIP polyglot, a 65,535-pixel PNG bomb, a WAV with forged sizes, MP3 noise, an HLS playlist, a concat list and an MP4-signed playlist pointing at a sentinel file, a forged WebP, an empty Ogg) go through the real import path with contained ffprobe. Each imports cleanly (the polyglot, as its video) or fails as MEDIA_INVALID within the probe limit; no result carries the sentinel's contents, the sentinel is unchanged and no grant remains. **Found and fixed:** a picture whose size the decoder could not read (the PNG bomb, the forged WebP) was imported as a 0x0 image; it is now refused. The corpus is bounded: it exercises the probe, not every decoder, and a real FFmpeg exploit is not part of it (the stand-in hostile worker covers what code running in the worker could reach).
- **Network isolation** relies on Windows' AppContainer network filtering (Windows Filtering Platform), tested here for TCP to loopback and the local network; UDP and other protocols are not separately tested.
- **Same-account programs.** Other programs of the same account can still read what the account can, including the tools folder and the workspace; the container constrains workers, not the account.
- **Crash leftovers.** If procd dies, capability entries stay on granted paths; they name a capability no later token holds, and the service's start-up tree reset removes those inside the workspace. Paths outside the workspace (a temporary current directory) keep the inert entry.
- **Untested brokers / permanent grant** (from T9c): only the listed brokers were tested; `grant_owner_full` still adds a full-control entry for the user where it labels a folder that was not private.

**Release-blocking** (founder continuation directive, 2026-10-13; [decision record](FOUNDER_DECISION_RECORD.md#2026-10-13-continuation-to-verified-completion)): read containment is implemented with an AppContainer and shown for a stand-in hostile worker and a bounded hostile-media corpus on this machine's development profile; the gate still needs the run on the release artifact and a clean profile.
