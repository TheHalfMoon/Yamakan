## T9c surface (merged)

- **Worker sandbox (closes the T4a WMI release blocker).** procd now launches every worker with `CreateProcessAsUserW` and a restricted copy of its own token. The copy has every privilege removed (bar change-notify), Administrators deny-only and Low integrity. No privilege is needed: a restricted copy of the caller's token is allowed, and lowering integrity is always allowed. The worker still runs suspended inside its kill-on-close, single-process Job Object as before.
- **Evidence:** from an ordinary process of this account, WMI `Win32_Process.Create` starts a process outside any job (control). From a sandboxed worker the same call is denied ("Access to a CIM resource was not available to the client", WBEM_E_ACCESS_DENIED 0x80041003), and nothing starts, although the marker was placed in a folder the worker could write. The security review also found Task Scheduler, BITS, DCOM activation (ShellWindows), the HKCU Run key, %TEMP%, other projects, hard links to the token and loopback listeners denied to a worker.
- **Writes are confined.** A worker can only read, except in the folders its request names (`writable` in RunOptions; at most 8, absolute, existing, not a link or junction): a `worker/` subfolder of the render's and the conversion's staging folder. procd labels them Low integrity just before launch, counting how many live workers hold each folder, and restores the default label when the last of them exits and when procd shuts down, then resets the folder (and everything in it) to plain inheritance from its parent, which removes access entries the worker added to its own folder. procd then checks that every object in it is readable and holds only inherited entries in an unprotected DACL (the reset can report success without reaching an object it was denied). If a folder cannot be restored (it is gone, became a link, or the worker locked it or anything in it), the run fails with RECOVERY_REQUIRED instead of passing silently. After a crash of procd itself, the service clears every integrity label in the workspace at its next start (the same tree reset that makes it private). To label a folder the account owns but lacks WRITE_OWNER on (an unrestricted folder, as in tests), procd first grants the owner full control of that folder, which an owner may always do. A workspace the service opened already grants it (T9b). Writes elsewhere fail with EPERM (tested).
- **Protocol:** `SPAWN id exe cwd jobMemoryBytes writableCount dir... argc arg...`.
- **Published files carry nothing the worker chose.** A worker owns the file it writes and could give it its own permissions or alternate data streams. The service keeps only the main data stream, copied into a file it creates in the staging folder above `worker/`, which the worker could never write or re-permission; the copy inherits the workspace's owner-only access (`keepMainStream`, used for exports, previews and VFR conversions, which are probed and imported from the copy). Tested with a protected Everyone DACL and a hidden stream on the file, and with a worker granting Everyone inheritable full control of its own folder.
- **Residual:**
  - A sandboxed worker can still **read** everything this account can, because the user SID is enabled: the client token, the launch secret (with which it could open a browser session against the local service), `workspace.sqlite` and every project's media. It also has network access.
  - While a worker runs, other low-integrity programs of the same account could write in its output folder.
  - Only the brokers above were tested; Low integrity is not an AppContainer.
  - A compromised worker holds WRITE_DAC on its own folder and can lock it against the owner (an OWNER RIGHTS entry); procd then cannot restore it, the run fails with RECOVERY_REQUIRED, and the next start refuses the workspace until an administrator resets that folder (takeown, icacls /reset). Beyond availability: in a folder it has locked, the worker could also leave copies of what it can read (token, launch secret, media) readable to another local account that knows the folder's full path (it contains random project and job IDs; the parents are not listable by other accounts) until the folder is reset. Tests cover a folder removed mid-run; lock cases below the folder are checked by the same walk the workspace helper uses, without a test that would leave undeletable folders. A write-restricted worker token (Modify on its folder for a restricting SID, never WRITE_DAC) would remove this; an attempt showed that some programs cannot start under one without further brokering, so it is open work.
  - An AppContainer or restricting SIDs (brokering every input file) would close these. That is open work, not done in this MVP step.
  - `grant_owner_full` adds a permanent full-control entry for the current user to a folder it labels, placed after explicit denies; this only happens where the folder was not already private.

## T9b surface (merged)

- **Session only through the launch link, never a cookie.** Opening the page grants nothing. The service writes `http://127.0.0.1:<port>/#launch=<secret>` to the owner-only `launch` file (it prints the file's location, not the secret). The page exchanges the secret (in the fragment, never sent to a server) through `POST /api/v1/session` (exact Origin required) for a session and a media key, kept in the tab's `sessionStorage`. API requests send the session as `X-Yamakan-Session` (state changes also need the exact Origin; any request from another site or loopback port is refused by Fetch Metadata); media elements and the export download carry `?media=<key>`, accepted only for GET asset, preview and artifact reads. No cookie is used because browsers send cookies to every port of 127.0.0.1, so another local server would receive one. Without a session the editor shows a sign-in notice (English and Arabic); each tab needs the link.
- **Owner-only workspace.** At start the service makes the workspace private before writing any secret, and refuses to open one it cannot. On Windows (`yamakan-acl`, dependency-free Rust built with procd):
  - a link or junction, or a folder owned by another account, is refused;
  - the root gets a protected DACL granting full access only to the current user, SYSTEM and Administrators;
  - the whole tree below is reset to inherit only that (explicit and protected entries removed) and owned by the current user;
  - every object is then checked, because the reset can report success without reaching every object.

  On POSIX the folder is 0700 (links and other owners refused), with secret files 0600 written fresh. The recovery folder, restored roots and migrated workspaces are restricted the same way. `core/process/access.ts` joins the spawn allowlist to run the helper.

- **Evidence for "second Windows account denied" without creating accounts:** `yamakan-acl probe-other` opens a path under a restricted copy of the service's token with the user and Administrators deny-only and no privileges. It keeps this logon's other groups, so it holds at least what another standard account holds and a denial is conservative.
  - From a known permissive start, the workspace, the token, a file with an explicit Everyone grant and a file with a protected Everyone DACL are all readable before and denied after.
  - An ordinary file stays readable (control), and a junction is refused.
  - The running service's workspace, token, launch file and database are denied, with the root's DACL and owner asserted.
  - It says nothing about an elevated administrator, who can always read. A real second-account check remains a T10 founder step.
- **Other loopback port:** in the E2E a page on another 127.0.0.1 port, in the same browser and even holding the real session and media key, can neither call the API nor load media, while the same requests succeed from the Yamakan page (control); the other port's server never receives the session, the media key or any Yamakan cookie.
- Cost and limits: every start (and backup) re-applies and re-checks the whole tree (measured about 0.05 s for a small workspace and 3.8 s for 40,000 files, against the plan's reopen target of 2 s); a marker-based fast path is open. Paths are passed in extended-length form, so deep workspaces work. Files below the root owned by another account are taken over (the root's owner check decides whose folder it is); handles another account opened before the first restriction are not closed, as the README says.
- Authenticated CLI (token file) works against the hardened service. In the keyboard-only journey in Arabic (RTL), Tab reaches the backup button and Enter runs it.

## T9a surface (merged)

- `core/recovery.ts`: a backup is the database copied online with SQLite's backup API from a separate read-only connection in one step (the copy holds everything committed when it began; the service keeps committing meanwhile), then every ready media object it registers, re-hashed as copied, then a manifest (`backup.json`, `yamakan.backup/1`) written last; a folder without a manifest is listed as incomplete and cannot be restored. While a backup runs, the store holds objects: nothing deletes an object file (a released staged version's file is left for garbage collection).
- Backups leave out the client token, the service lock, exports (an export of a restored workspace is made again; its download says so), staging and preview caches, as each manifest states. Damaged media found while backing up is recorded in the manifest and not copied; the source file is left as found.
- Restore builds a new, empty root only, after a free-space check (counting in-flight imports), one recovery operation at a time, at most 20 restores per backup. The database must match the manifest's hash, version and project heads; every object the database registers as ready must be verified against its content address, and anything else (damaged, malformed, unlisted or altered in the backup) is quarantined (registered, never served) and listed in `restore.json`. A failed restore removes only what it made. The manifest sits beside the copy, so its hashes detect corruption and partial copies, not deliberate tampering; the receipt names the manifest's hash for an out-of-band check.
- Service commands (no host paths accepted; folders chosen by the service under `YAMAKAN_RECOVERY`, default `<workspace>-recovery`, which must be outside the workspace): `yamakan.workspace.backup`, `.backups`, `.restore` (by backup id, into `restored/<id>-<n>`), `.collectGarbage`. The project list has a Backups panel (back up, list, restore into a new folder) in English and Arabic.
- `core/wal.ts` inspects a write-ahead log read-only: SQLite stops at the first damaged frame without an error and deletes the log at the next checkpoint, losing later commits. With `synchronous=FULL` every commit but the last was synced, so damage is proven only when a current-generation frame follows a lost commit frame (reported with the commits that would be lost); an unreadable tail that is only the last, unsynced transaction is what a power cut leaves and opens normally (damage confined to that transaction cannot be told apart and is not reported). The service refuses a damaged log with `RECOVERY_REQUIRED` before opening anything, so it stays as found; a damaged database file is refused the same way instead of with a raw SQLite error.
- `npm run recovery -- diagnose <workspace> [--verify-objects] [--scratch <folder>]` reads a workspace without changing it (log inspected in place, database and log examined as copies, malformed rows reported); `restore <backup> <new folder>`; `backup <workspace>` while no service runs, reading the database as it is (never created or upgraded).
- Garbage collection (at service start and on command) removes only crash leftovers older than an hour: unregistered objects, object-store temporary files and upload staging files; never a registered object, never during a backup, and not in a project with a publication in flight.

## T4a surface (merged)

- `native/procd` (Rust, no dependencies): owns probe workers now; FFmpeg rendering moves onto it in T5. Each worker is created suspended inside its own KILL_ON_JOB_CLOSE, single-process Job Object (atomic `PROC_THREAD_ATTRIBUTE_JOB_LIST`, no breakaway), with an inherited-handle allowlist, a minimal environment, an executable allowlist and MSVCRT-exact argument quoting. Output travels over anonymous pipes relayed by procd (no named objects). Workers resume only after the service records their identity. Service death → procd stdin EOF → jobs terminated; procd death → the OS closes the jobs.
- `core/process/owner.ts` + `workers.ts`: one owner per service; FFmpeg/ffprobe resolved to absolute paths once. Non-Windows hosts run an explicitly unqualified development mode.
- `probe()` runs through the owner: file-only protocol whitelist, wall-clock and Job memory limits, bounded output, `MEDIA_INVALID` without paths. Records time base and frame rate and identifies VFR.
- Windows evidence: argv fidelity, minimal env, suspended-until-recorded, cancellation, service kill, owner kill, owner death between create and resume, and service death during identity recording all leave no live or suspended worker; a worker cannot start children; malformed protocol input is refused.

## T3 surface (merged)

- `core/time.ts`: integer flicks (705,600,000/s) with BigInt intermediates, explicit rounding and safe-integer checks; frame/PTS/time-base conversions.
- `core/canonical.ts`: `yamakan.project` formatVersion 1 (flicks, rational fps, language, source time base). Newer versions are inspectable but never edited or rewritten. The 30 fps editing shape is a lossless projection; unrepresentable values fail with `CAPABILITY_UNAVAILABLE`.
